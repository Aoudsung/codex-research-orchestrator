# Proposed v0.2 update: sustained collaboration through optional MCP bridges

Status: accepted design record for v0.2.0. Shipped behavior and verification are recorded separately in [release validation](validation-v0.2.md).
Prepared: 2026-10-25. Baseline: v0.1.1.

Implementation was authorized on 2026-10-25. This document retains the accepted design. The shipped release uses Node.js 24 or later; its actual checks and limitations are recorded in the release validation notes.

## Scope and purpose

Update Codex Research Orchestrator to reflect the author's recent collaboration practice: parallel research partners, independent discussion groups, focused review, external implementation authors, compact handoffs, and event-driven continuation.

The update concerns this public skill and an optional, sanitized copy of the author's MCP bridge. It does not change a research method, experiment, project state, running job, or the live bridge installation. No private research materials or existing bridge database belong in the distribution.

The research purpose remains unchanged: identify the key scientific question, preserve the user's requirements, and support substantive innovation through inspectable evidence. Coordination efficiency serves that purpose; fewer tokens or more completed tool calls do not establish better research.

## What is already present

Version 0.1.1 already provides research roles, independent-input boundaries, claims and decisions, scoped review, source-backed memory, context budgets, persistent records, atomic state-file replacement, and compact handoff guidance. Keep these mechanisms and extend their operational contracts. Do not present them as new features or replace the existing memory tool without a concrete need.

## Changes to the collaboration model

| Area | Recent practice to retain | Public rule |
|---|---|---|
| Research partners | Different partners work on complementary questions in parallel | Assign separable scientific questions; form independent judgments before exchanging evaluations when independence matters |
| Discussion groups | A group can distribute work and develop a distinct candidate | Make delegation policy configurable; preserve ownership, source boundaries, and the lead's scientific decisions |
| Implementation | An external author handles code analysis, implementation, self-checks, and repairs | In delegated execution mode, Codex coordinates, combines feedback, verifies relevant evidence, and accepts the result without repeating the author's entire workflow |
| Review | A reviewer closes specified findings on a specific revision | Record version, covered claims, conditions, and open findings; reuse unchanged coverage |
| Continuation | Persistent tasks and sessions are reused across revisions | Preserve task, participant, conversation, and required-model bindings; send only new requirements and evidence |
| Notifications | Capable channels deliver events; channels without push use scoped scheduled checks | Use the channel's actual capability, not one polling policy for all participants |

Roles remain configurable responsibilities. The default workflow must not require a fixed team size, provider combination, model name, or discussion hierarchy. Respect user-specified participants and models when they exist. Native Codex collaboration remains usable without an MCP runtime.

## Optional MCP runtime

The inspected local bridge has three entry points: Codex, Claude Code, and Antigravity. They share a core for tasks, messages, permission preflight, structured patches, validation records, and delivery tracking. At inspection time, this Codex session exposed the Claude Code and Antigravity adapters; the local Codex server existed but was not connected here.

Reuse that shared implementation in a sanitized optional runtime. Keep provider-specific execution and host-wakeup drivers separate from the research rules. Do not clone live tasks, conversations, inboxes, permission leases, or notification routes.

Skill discovery or installation must not run a global configuration writer, register every provider, start a daemon, or change account permissions automatically.

## Task and delivery contract

### Stable bindings

For external work, record the logical task, participant, required model, execution session, permitted workspace, and current artifact revision. Check the actual tool schema before use.

Create a task explicitly before execution and continue it through revisions. Existing task creation currently returns the old task when the ID is reused; it does not update its constraints. A changed scope must use an explicit supported amendment or remain unresolved, not be assumed to take effect because new arguments were sent.

Distinguish the requested model from a model reported by runtime metadata. An invocation flag is not independent confirmation of the model that ran. Preserve the evidence level and reject a known mismatch. When a user requires verified identity and the backend cannot provide it, report that limitation rather than silently substituting a model or relabeling a request as verification.

### Preflight and authority

Before dispatch, check tool compatibility, required read and write paths, and the permission delta for the actual execution mode. Preflight describes what is needed; it cannot create human authorization or replace the host sandbox.

Explicitly set write scope for code tasks. A read-only task must not acquire general write access through an empty scope. Revoke only task-created permission changes when work ends, preserving pre-existing user settings.

Incompatible direct-write tools may lead to an authorized structured-patch mode, but only after that mode passes its own checks. Do not mark the original incompatible execution plan as successful or repeatedly retry a deterministic tool error.

### Incremental handoff

The first handoff supplies the goal, original requirement sources, permitted materials, execution boundaries, required output format, and completion conditions. Later handoffs supply the current artifact revision, applied or superseded patches, changed files, new evidence, and remaining findings.

Use compact summaries and artifact references by default. Fetch the exact patch or full source only when application or a specific judgment needs it. Preserve the original artifact separately; never reconstruct it from a truncated log.

An optional read-set records which file version or range the author already inspected. Reuse it only while that material is unchanged. A read-set aids context reuse and does not grant access or establish independent review.

### Delivery, verification, and acceptance

Keep the following meanings distinct:

| State | What it establishes |
|---|---|
| Submitted | A request was stored or dispatched |
| Received | The intended participant or bridge received it |
| Delivered | The declared artifact set and completion receipt are available |
| Applied | The indicated patch set was actually applied |
| Validated | The relevant checks passed for that artifact set |
| Reviewed | Specified findings and claims were reviewed for that version |
| Accepted | The accountable lead accepted the declared scope |

These are evidence distinctions, not mandatory stages for every task. A theoretical analysis need not produce a patch or run tests. Design acceptance remains conditional on its stated assumptions; it is not empirical confirmation of research benefit. A CLI exit code of zero does not establish delivery or acceptance.

Use `completeTaskOnExit: false` explicitly for provider executions that await validation or review. Do not depend on differing backend defaults.

Structured patches retain the author's original content, target scope, dependencies, replacement relation, and validation association. Missing dependencies, cycles, incompatible bases, or unauthorized paths must block application rather than be silently ignored.

For multi-part delivery, associate the artifact list and final receipt with a delivery revision. A quiet coalescing window can collect adjacent events, but cannot prove completeness. An incomplete set remains partial even if the sender has been quiet.

## Continuation without repeated polling

Support two distinct modes:

1. **Wait within the current turn.** When the caller needs the next delivery before proceeding, use the bridge's integrated delivery wait. One dispatch can collect patches and the receipt, then return for the next necessary validation. Yield to the host while waiting when supported; do not create duplicate requests or another polling loop.
2. **Resume in a later turn.** A persistent host receiver may deliver new work to the bound chat. The current environment has observed and user-confirmed this capability. A new installation must establish its own compatible route; past success is not proof for every client.

Store separate progress for message receipt, host acceptance, and processing by the target chat. Inbox insertion, a local waiter callback, or a forwarding command's exit status cannot alone establish a new chat turn. A successful host receipt must identify the accepted target and turn or the documented equivalent.

After independent participants have taken over the necessary work and the lead has no remaining action, the lead may finish the current turn. This does not mean that the delegated research is complete. On a genuine return event, resume the bound task and retain final acceptance responsibility.

For a channel without push notification, allow a user-authorized scheduled check of that channel only. The current project's interval can be represented as a sample setting, not a universal framework constant. Reuse its schedule, stay quiet when unchanged, and disable it when no response is pending. Do not extend it to all implementers or reviewers.

The existing bridge profile uses a 2,500 ms coalescing window and a 600,000 ms delivery-wait default. Keep such values configurable and reconcile them with the actual client deadline. An earlier client timeout does not mean work failed or completed: preserve the binding and cursor, then perform only the bounded reconciliation needed to decide whether the original task is still active.

Use task-scoped cursors and artifact revisions to ignore old deliveries. Preserve the ability to resume after interruption without replaying an already applied patch. Receiving an event is not authority to start unrelated work.

## Memory and context integration

Keep two separate sources of state:

- Research files and the existing memory helper hold authoritative requirements, scientific claims, decisions, evidence, and durable checkpoints.
- The bridge holds execution bindings, message cursors, permission leases, artifact deliveries, and validation status.

Research state references a task and its accepted results; it does not copy the entire inbox or patch history. A scientific conclusion enters research memory only after the lead records its meaning and evidence. Transport success cannot promote an evaluation into a fact.

Use the existing `checkpoint` record for a concise continuation pointer. No new memory kind or schema migration is required just to store task IDs or artifact references. Continue to build recipient-specific context packets; an independent reviewer must not receive the general execution inbox or prior evaluations.

Add purpose-specific handoff sections for research, review, implementation, and repair. Put the question and output contract first, include relevant current evidence, and keep unrelated provider instructions or SDK descriptions out of the packet. Retain raw source text separately rather than repeatedly nesting escaped JSON inside prompts.

## Source corrections needed before public runtime distribution

The following differences were identified while preparing the plan. They define the source-adaptation work; the release validation record reports the implemented checks:

| Observed behavior | Required change in the distributed copy |
|---|---|
| Database initialization seeds a private task-to-chat wakeup route | Remove the seeding behavior entirely; a fresh install starts with no task, target chat, or enabled route |
| Preflight's `ok` depends only on missing read roots, while other checks are informational | Compute readiness for the selected delivery mode from its actual required tools and paths; report unmet conditions accurately |
| Empty patch write scope permits general relative paths | Give read-only and explicitly scoped writes distinct, unambiguous behavior |
| Missing conversation metadata may pass binding checks; requested model flags can be recorded as actual identity | Preserve identity evidence levels and enforce the user's stated binding requirement without silent substitution |
| Patch ordering skips missing dependencies and cycles | Validate prerequisites before declaring a patch set ready to apply |
| Some confirmation paths accept weak receipts or forwarding success | Separate forwarding from host acceptance; require the appropriate target-turn evidence for confirmed wakeup |
| Backend completion defaults differ | Precreate the task and explicitly retain it until the required delivery and validation are complete |
| Package/server versions and documented tool counts differ | Make published metadata match the shipped code and schemas |

Apply these changes only to the new runtime inside this repository. Preserve the live source installation and its operational state.

## De-identification and release boundaries

Remove private filesystem roots, research names, real task/chat/message IDs, internal URLs, host addresses, default routes, generated account configurations, live databases, logs, and daemon state. Do not replace a private route with a fictional route that is still automatically enabled.

Use synthetic fixtures and neutral task names. Move database paths, CLI executables, provider models, working directories, sockets, host URLs, session bindings, and wakeup drivers into local configuration. Keep public provider and tool names when needed for compatibility.

Retain the public repository's author attribution. Include the runtime under the repository's MIT arrangement for the author's own code, with an explicit license file and package field. Preserve any applicable third-party notices discovered during source extraction; the original local package currently has no license file or license field.

Do not import the private source repository's history, research snapshots, or configuration directories. A source copy and release manifest should enumerate only the selected runtime, tests, examples, and documentation.

## Implementation order and acceptance

First revise the skill's collaboration contract and project template. Then extract and sanitize the shared runtime, fixing the concrete contract gaps before packaging it. Integrate the compact context and receipt flow, run focused checks, and publish a new version only after the claimed capabilities have corresponding evidence. This order follows dependencies; it adds no per-step user approval process.

Acceptance should cover:

- Fresh initialization creates no seeded private task, route, global configuration change, or hidden background listener.
- A task preserves its explicit participant, model requirement, and conversation through follow-up work; mismatches and unknown identity evidence are reported correctly.
- Read-only, write-scoped, and structured-patch execution modes enforce their own declared readiness and path boundaries.
- Superseded patches, missing dependencies, cycles, and duplicate notifications cannot cause the wrong patch set to be applied.
- A passing CLI process without a complete receipt does not close work awaiting delivery or validation.
- A failed validation produces one consolidated repair handoff to the original task, with the affected artifact version and relevant failure evidence.
- Summary interfaces remain bounded as the inbox and patch history grow; exact artifacts are fetched separately.
- Message receipt, host acceptance, and target-chat processing are distinguished. An explicitly authorized idle-chat check establishes the installed wakeup route; unsupported hosts remain reported as unsupported.
- A channel-specific scheduled check stays quiet without change and stops when the pending response is resolved.
- A provider-free installation still supports the existing native Codex workflow and memory tests.

Use isolated synthetic tasks for bridge checks, never an active research job. Mock contracts can establish routing and state behavior; claims of live host wakeup need a real, authorized host check. Do not repeat unrelated research experiments, numerical-method tests, or already covered acceptance work.
