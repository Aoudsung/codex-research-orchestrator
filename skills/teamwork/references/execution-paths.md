# Teamwork execution paths

Choose the path from the requested deliverable. A delegated project coordinator stays within the approved objective even when a local milestone suggests a broader change.

| Path (`specification.route`) | Organize the work | Evidence at acceptance |
|---|---|---|
| General (`general`) | Map requirements to versioned milestones. Check architecture or interfaces early when they couple tracks. Assign parallel owners only over independent scopes. Separate final verification from authorship and assign one runner for shared expensive checks. | Matched requirements, live integration or real artifact checks, known failures with affected scope, and independent audit of the current versions. |
| Light engineering (`light_engineering`) | Use a short owner → independent check → acceptance chain for a small, well-understood change explicitly requested as Teamwork. Add a milestone only for a real dependency. | Reproduce the original case and verify the actual entry point and relevant integrations. |
| Paper or document review (`document_review`) | Freeze the manuscript version and review criteria. Give independent readers distinct high-impact questions. Preserve blinded first assessments where applicable. Synthesize only after those assessments are recorded. | Exact passages or claim IDs, decisive source or reproduction evidence, and a verdict on corrections, qualifications or unresolved claims. |
| Informal mathematical proof (`informal_math`) | Record hypotheses, quantifiers and target. Ask for independent construction or counterexamples when they can discriminate. Audit the hard implication, boundary conditions and use of all assumptions. | A complete argument with cited lemmas or an explicit unresolved implication and any counterexample. |
| Large proof (`team_math`) | Use this path only when the user opts in. Declare the resources, partition only independent lemmas, and agree on interfaces before distributing construction. Use fresh checking and integrate assumptions and dependencies. | Coherent proof under the original hypotheses, with independently checked critical lemmas and the original statement preserved. |
| Lean proof (`lean4`) | Use when the user specifies Lean. Freeze the theorem statement and check existing project conventions. Assign separate lemmas only where imports and namespaces permit. Report any additional axioms or admitted results. | The current theorem checked by the project's Lean toolchain and a record of assumptions, admissions and build result. |

For a failed check, send evidence and the acceptance criterion back to the member who can repair it. A successor reads the approved objective and latest receipts before reading older discussion. Preserve prior failures as evidence, then use the existing ready graph to resume rather than reissuing completed assignments.

## Large projects with per-assignment Boost

A request for a very large team applies to research and general projects as well as to formal proofs. Set `specification.strategy.teamSize: "large"` and derive the lanes from real components, environments, methods, or independent questions. Use `maxParallel` within project and provider limits, assign each expensive shared resource one owner, and start work in waves when a dependency or resource blocks parallel dispatch. Grow the team as independently useful work appears.

For a Teamwork request that calls for Boost across its subagents, set `specification.strategy.boostScope: "substantive_tracks"` and keep the candidate and fresh challenger in separate sessions for each substantive assignment, including delegated integration or audit. A counterexample routes the criteria and evidence back to the owner. Reopen the affected candidate and repeat the challenge on the repaired version. Preserve the applicable evidence when the challenger finds no failure. Keep the versioned result connected to the milestone that consumes it. Project-level independent acceptance checks the deliverable and its consistency with shared contracts and comparison conditions. Carry the protocol forward to new members and successor leads. Primitive authors and challengers execute their own bounded assignments directly.

A comparative study should track one cell per requested model tier and environment. For each cell, match the baseline's parameter budget, task definition, data and splits, information and tool access, interaction, training and inference budgets, tuning opportunity, seeds, metric aggregation, and evaluation versions. Record any mismatch and its effect on the claim. Reaching SOTA in measured cells supports those cells. A claim across all model sizes requires separate evidence or argument. Keep any cell with missing comparative evidence open. Model and compute usage follow the actual approvals for the project.

For a best-known performance claim, register the eligible competitors, their source versions, and the grounds for including or excluding each one before interpreting the scores. When only one matched reference could be reproduced, limit the finding to that comparison and record the remaining competitors to check. An independent auditor reopens the claim if a newly eligible reference changes the comparison.

Freeze the matrix with `specification.comparisonProtocol`. It contains `purpose` (`design` or `measurement`), `dimensions` (a map of axis names to listed values), `matchFields`, and optional `openDimensions`. In the final step receipt, `comparisonEvidence` uses `scope: "listed"` and `cells` with `at` coordinates and a `status` of `planned`, `observed`, `unmatched`, or `unmeasured`. Each matched cell has candidate and baseline `settings` and `evidenceRefs`. Each observed arm adds a finite `value`, its own `resultRef`, and a matching `metric: {name, direction, unit}` where direction is `higher` or `lower`.

The audit links each reference to evidence on its final step receipt. Complete design delivers matched plans or observations across all cells. Complete measurement requires observations for all cells. Unavailable or unmatched comparisons need a reason. If a partial report omits cells, give the reason in `comparisonEvidence.reason`. An optional observed `comparison` cites both result references in `evidenceRefs` and records a point-value `outcome` of `candidate_better`, `baseline_better`, `tie`, or `inconclusive`. Report uncertainty and generalization within the scientific evidence.
